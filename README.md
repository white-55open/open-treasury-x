# open-treasury-x（OTX）

开源 Web3 财务管理中间件。让业务系统快速获得账户、流水、总账、对账等资金管理能力，无需从零构建。

---

## 功能模块

| 模块 | 一句话描述 |
|------|-----------|
| **账户管理** | 用户资金账户的开户、余额查询、金额冻结与解冻 |
| **充值** | 用户链上充值到账后的余额增加、流水记录和总账入账 |
| **提现** | 用户提现申请的余额冻结、链上确认、金额扣除和总账入账 |
| **资金流水** | 每一笔资金变动的明细记录，append-only 不可篡改 |
| **总账** | 复式记账系统，为每笔业务生成会计凭证，支撑审计和报表 |
| **链上查询** | 查询区块链交易状态和确认数，为充值/提现/对账提供链上依据 |
| **对账** | 自动检测账务不一致（流水 vs 总账 / 链上 vs 链下）并修复 |

## 模块详情

### 账户管理

管理用户资金账户的可用余额和冻结余额。

| 接口 | 调用场景 | 状态 |
|------|----------|------|
| 创建账户 | 用户注册时调用。系统为该用户创建一个资金账户，初始余额为零。同一用户重复调用不会报错，幂等返回已有账户信息。 | ✅ |
| 查询账户 | 用户查看资产、风控检查余额时调用。返回可用余额和冻结余额。 | ✅ |
| 增加可用余额 | 运营手动加钱、系统内部调账、发放奖励时调用。增加用户的可用余额，不影响冻结余额。 | ✅ |
| 冻结余额 | 用户发起提现申请时调用。将指定金额从可用余额转入冻结余额，防止用户重复消费同一笔资金。不能超过可用余额。 | ✅ |
| 解冻余额 | 提现申请被拒绝、用户取消提现、风控解除时调用。将冻结余额退回可用余额。不能超过冻结余额。当前通过提现解冻端点（POST /withdraw/unfreeze）实现，记录 UNFREEZE 流水并过账解冻凭证。 | ✅ |

### 充值

用户将链上资产转入平台后，系统为其增加余额并完成会计入账。

| 接口 | 调用场景 | 状态 |
|------|----------|------|
| 充值入账 | 链上充值交易达到确认数后，业务系统通知 OTX 入账。系统依次：增加用户可用余额 → 记录流水 → 总账生成凭证（借记充值在途，贷记用户可用余额）。 | ✅ |
| 充值幂等 | 同一充值订单号（bizNo）重复调用时，系统不会重复加钱或重复过账，返回原始成功结果。由数据库唯一索引和业务层双重保障。 | ✅ |
| 过账失败容错 | 第三步总账过账如果失败，前两步的余额变更和流水记录不回滚。过账失败记录日志，后续通过对账模块修复凭证缺失。 | ✅ |
| 入账前链上确认检查 | 充值入账前先调用链上查询接口，确认链上交易已达到配置的安全确认数（如 12 个确认）。防止未确认或孤块交易入账。 | ⏳ |
| 充值资金归集 | 充值入账完成后，将资金从充值在途科目转入平台热钱包科目。完成资金从在途到可用的会计闭环。 | 📅 |

### 提现

用户申请将资产提走到外部地址。

| 接口 | 调用场景 | 状态 |
|------|----------|------|
| 提现冻结 | 用户提交提现申请时调用。从可用余额中锁定申请金额转入冻结余额（POST /withdraw/freeze），记录 FREEZE 流水并过账冻结凭证（借记用户可用余额，贷记用户冻结余额）。防止审核期间用户消费。 | ✅ |
| 提现结算 | 提现申请审核通过后调用。从冻结余额扣减（POST /withdraw/settle），记录 WITHDRAW 流水并过账结算凭证（借记用户冻结余额，贷记提现在途）。仅校验冻结余额，允许全额结算。完整流程：冻结 → 广播（POST /withdraw/broadcast）→ 链上确认结算（POST /withdraw/{bizNo}/confirm-settle）/ 取消（POST /withdraw/{bizNo}/cancel）。 | ✅ |
| 提现幂等 | 冻结/结算/解冻各阶段以独立业务号（bizNo）幂等，重复调用不重复动账、不重复过账。由唯一索引和业务层双重保障。 | ✅ |
| 过账失败容错 | 总账过账如果失败，余额变更和流水记录不回滚。过账失败记录日志，后续通过对账模块修复凭证缺失。 | ✅ |
| 取消提现 | 提现申请被风控拒绝、审核不通过或用户主动取消时调用。将已冻结余额释放回可用余额（POST /withdraw/unfreeze），记录 UNFREEZE 流水并过账解冻凭证（独立凭证，不冲销原冻结凭证）。 | ✅ |
| 链上确认检查 | 平台向链上发出提现交易后，等待交易达到确认数。确认检查在 confirmAndSettle 内通过 ChainQueryPort 完成，确认达标后完成最终结算（POST /withdraw/{bizNo}/confirm-settle）。 | ✅ |
| 扣除手续费 | 提现时按规则计算手续费，优先从提现金额中扣除手续费再扣减本金。手续费收入记入充值手续费收入科目。 | 📅 |
| 记录 Gas 费 | 链上提现消耗的 Gas 费记录到 Gas 费支出科目。 | 📅 |

### 资金流水

记录每一笔引起余额变化的业务事件。一旦写入不可修改或删除。

| 接口 | 调用场景 | 状态 |
|------|----------|------|
| 记录流水 | 充值、提现、冻结、解冻操作自动触发。每条流水包含：变动金额、变动前余额、变动后余额、资金方向（入/出）、资金类型（充值/提现/冻结/解冻）。 | ✅ |
| 按用户查询流水 | 客服查询用户资金流水、风控分析用户行为时调用。返回该用户的全部流水记录，按时间倒序排列。 | ⏳ |
| 按业务号查询流水 | 根据充值订单号或提现单号定位单笔流水的详细信息。用于对账和问题排查。 | ⏳ |

### 总账

复式记账系统，每笔业务事件生成一张会计凭证，保证借贷平衡。

| 接口 | 调用场景 | 状态 |
|------|----------|------|
| 凭证过账 | 充值、提现发生时自动调用。创建一张凭证，包含两条以上的借贷分录，系统自动校验：借贷金额合计相等、同一科目在同一方向不重复、金额为正数。 | ✅ |
| 按业务号查询凭证 | 财务审计时根据业务号查询完整凭证信息，包含所有分录行。 | ✅ |
| 凭证冲销 | 发现已过账的凭证有误时调用。系统生成一张与原凭证分录借贷方向相反的新凭证，并将原凭证状态标记为已冲销。原凭证不可删除。 | ⏳ |
| 凭证列表查询 | 按业务类型（充值/提现/转账等）、记账日期、凭证状态等条件筛选查询凭证列表。用于财务做账和审计抽检。 | ⏳ |
| 分录明细查询 | 按用户 ID 或会计科目查询所有关联的分录。用于计算某个用户的全部账务影响或统计某个科目的汇总金额。 | ⏳ |

**会计科目一览：**

| 科目 | 类别 | 用途 |
|------|------|------|
| 用户可用余额 | 负债 | 用户可自由支配的资金 |
| 用户冻结余额 | 负债 | 提现中或锁定中的资金 |
| 充值在途 | 资产 | 用户已充值但未归集到热钱包的资金 |
| 提现在途 | 负债 | 已扣减但尚未发出的提现资金 |
| 平台热钱包 | 资产 | 平台在线可动用的资金 |
| 平台冷钱包 | 资产 | 平台离线存储的资金 |
| Gas 费应付 | 负债 | 尚未支付的链上 Gas 费 |
| 充值手续费收入 | 收入 | 收取的充值手续费 |
| 提现手续费支出 | 费用 | 支付的提现手续费 |
| Gas 费支出 | 费用 | 链上交易消耗的 Gas 费 |

### 链上查询

提供区块链交易状态查询，被充值、提现、对账等模块内部调用。

| 接口 | 调用场景 | 状态 |
|------|----------|------|
| 查询交易回执 | 充值入账或提现结算前调用。检查某笔链上交易是否已打包、交易状态是成功还是失败。 | ✅ |
| 获取当前区块高度 | 计算交易确认数时调用。获取指定链的最新区块高度。 | ✅ |
| 判断确认数是否达标 | 入账前调用。指定交易哈希和所需确认数，系统自动查询当前块高并计算确认数是否 ≥ 要求值。确认数不足时返回 false，由调用方决定等待或降级。 | ✅ |
| 充值/提现流程自动调用 | 在充值入账和提现结算的流程中，自动插入链上确认检查步骤。确认达标后才继续后续操作。 | ❌ |

### 对账

自动检测账务不一致并修复。

| 接口 | 调用场景 | 状态 |
|------|----------|------|
| 流水与总账对账 | 每日定时运行。扫描资金流水表，检查每条流水是否在总账中有对应的凭证。发现缺失时输出差异报告。 | ❌ |
| 链上与链下对账 | 每日定时运行。扫描总账中携带了交易哈希的凭证，调用链上查询接口验证交易是否真实存在、金额是否一致。 | ❌ |
| 借贷平衡校验 | 每日定时运行。汇总所有科目的借方和贷方发生额，验证合计是否相等。不平衡时触发告警。 | ❌ |
| 自动补账 | 对账发现不一致时，系统自动生成调整凭证或冲销凭证修复差异。人工确认模式可选。 | ❌ |
| 对账报告推送 | 对账完成后输出报告，不一致项通过告警方式通知运维人员。 | ❌ |

## 一键体验（模拟用户个人中心）

仓库附带独立模块 [`mock-upstream/`](mock-upstream/)（**不加入主工程 Maven reactor**，仅通过 HTTP 调用 OTX REST API，模拟"用户 + 链上事件源 + 业务系统调用方"）。它提供**模拟用户个人中心页面**（`:8004`），业务动作由你亲手触发，每个操作都映射到具体用户操作：

| 你的操作（页面按钮） | 一键处理自动完成（内部流程） | OTX 接口 |
|---|---|---|
| 创建用户 | — | `POST /accounts/create/{uid}`（幂等开户） |
| 发起充值 | 确认数推进至达标 → 入账 | 模拟链 → `POST /deposit` |
| 申请提现 | 广播 → 确认 → 结算 | `POST /withdraw/freeze` → `broadcast` → `confirm-settle` |
| 取消提现 | 解冻资金回可用余额 | `POST /withdraw/{bizNo}/cancel` |

模拟链区块仅在点击「⚙ 一键处理」时按需推进（无定时推块），确认数演化过程折叠为页面操作日志；支持**多用户**创建与切换，各用户资产/记录独立；启动后**零自动调用**，全程节奏由你掌控。

**启动顺序：**

1. **启动 MySQL 与 Redis**（dev 环境依赖，见 `otx-starter/src/main/resources/application-dev.yaml`）：
   - MySQL：`localhost:3307`（库名 `treasury_test`）
   - Redis：`localhost:6380`
2. **启动 OTX**（dev profile，端口 8003）：
   ```bash
   .\mvnw.cmd -pl otx-starter spring-boot:run
   ```
3. **启动模拟上游**（端口 8004，提供个人中心页面）：
   ```bash
   cd mock-upstream
   .\mvnw.cmd spring-boot:run
   ```
   > mock-upstream 为独立应用，自带 mvnw，不参与主工程构建；可用环境变量 `OTX_BASE_URL` 覆盖 OTX 地址。
4. **打开模拟用户中心**：`http://localhost:8004`——创建用户 → 发起充值/提现 → 点击「⚙ 一键处理」→ 页面操作日志展示每一步的业务身份、HTTP 端点与 OTX 响应。
5. **打开管理控制台查看落账**：`http://localhost:8003/admin`（账户余额、资金流水、总账凭证与提现单据随你的操作逐步联动）。

**dev 环境说明（广播依赖）：** OTX dev 的提现广播依赖本地 keystore 签名（`classpath:keystore/dev-withdrawer.json`）与链上 RPC（`ALCHEMY_KEY` 环境变量）。若两者未准备，充值不受影响（充值入账走 Web3j RPC 确认，RPC 不可用时 OTX 会 fail-safe 拒绝入账，操作日志会展示该路径）；提现广播将返回 `FAILED` 状态——编排器打印实际结果，提现结算会失败、取消路径仍可完成，这本身也是"真实集成行为"的展示。准备 keystore 并注入 `OTX_KEYSTORE_PASSWORD` / `OTX_HOT_WALLET_ADDRESS` / `ALCHEMY_KEY` 后可演示完整广播成功路径。

**幂等验证：** 同一 bizNo 重复触发（如一键处理失败后重试）时，OTX 幂等兜底保证不重复入账、不重复动账，操作日志可见幂等返回结果。
