# mock-upstream 规范

## 目的

模拟上游（Mock Upstream）上下文提供 OTX 的**外部调用方模拟器**：一个独立运行的轻量 Spring Boot 应用（与 OTX 同仓库、不同端口 8004），模拟"用户 + 链上事件源 + 业务系统调用方"，通过 **HTTP 调用 OTX 的 REST API**（与真实上游完全同构）。它提供**模拟用户个人中心页面**：业务动作由用户在页面手动触发（创建用户 / 发起充值 / 申请提现 / 取消提现），每个操作映射到具体用户操作；系统内部步骤（确认数推进、入账、广播、结算、解冻）收敛为「⚙ 一键处理」按钮批量自动完成。配合管理控制台（→ admin-console）实现"你自己演给你看"。

不属于本上下文：OTX 主项目任何内部实现（模拟器零依赖、纯 HTTP 交互）、管理控制台展示（→ admin-console）。

## 需求

### 需求:系统必须提供独立的模拟上游模块

系统必须（MUST）在仓库根提供独立目录 `mock-upstream/`，作为 OTX 的外部调用方模拟器：独立的 Spring Boot 应用（独立 pom、独立端口 8004），**只通过 HTTP 调用 OTX REST API**，不得 import 任何 OTX 内部 Maven 模块或共享类。

#### 场景:独立启动
- **当** 在 `mock-upstream/` 目录执行 Maven 启动命令
- **那么** 模拟器作为独立进程启动（端口 8004），不依赖 OTX 的构建产物，仅需要 OTX 已在 8003 运行

#### 场景:只通过 HTTP 与 OTX 交互
- **当** 模拟器执行任何业务动作
- **那么** 所有与 OTX 的交互必须经由 HTTP REST 调用（`otx.base-url` 配置指向 OTX），源码中不得出现 OTX 模块的 import 或类型引用

### 需求:系统必须提供模拟用户个人中心页面

系统必须（MUST）提供基于 Thymeleaf 的模拟用户个人中心页面（`GET /`），作为 mock-upstream 的主交互界面。页面必须包含：当前用户资产卡片（可用/冻结余额）、充值表单、提现表单、一键处理按钮、我的记录列表（充值/提现记录及状态）、操作日志区、用户切换入口。

#### 场景:页面展示当前用户资产与记录
- **当** 用户访问 `GET /`
- **那么** 页面必须展示当前选中用户的可用/冻结余额、全部充值/提现记录（含状态标签与充值确认数）与操作日志（倒序）

#### 场景:页面操作全部映射具体用户操作
- **当** 用户在页面执行创建用户、发起充值、申请提现、取消提现
- **那么** 每个操作必须对应一个现实用户动作，操作日志必须记录业务身份说明、HTTP 端点与 OTX 响应摘要

### 需求:系统必须支持多用户创建与切换

系统必须（MUST）支持创建多个模拟用户并在个人中心间切换，各用户的资产与记录相互独立。

#### 场景:创建并切换用户
- **当** 用户提交 `POST /users`
- **那么** 系统必须幂等创建用户（重复创建返回已有用户）并切换为当前用户，资产初始为 0

#### 场景:切换已有用户
- **当** 用户提交 `POST /users/{uid}/select`
- **那么** 系统必须切换当前用户，页面展示该用户的资产与记录

### 需求:系统必须将内部处理收敛为一键处理按钮

系统必须（MUST）提供 `POST /internal/process` 一键处理入口：批量推进所有挂起事项（确认中的充值 → 推块达标 → POST /deposit 入账；已冻结提现 → 广播 → 确认 → 结算；取消处理中提现 → 解冻），并在页面展示处理统计。除用户操作（创建/充值/提现/取消）与一键处理外，系统不得自动调用 OTX 接口。

#### 场景:一键处理推进全部挂起事项
- **当** 用户点击一键处理且有挂起事项
- **那么** 系统必须依序处理全部"确认中"充值、"已冻结"提现与"取消处理中"提现，每步调用 OTX 并记录日志

#### 场景:启动后不自动调用 OTX
- **当** mock-upstream 应用启动且无任何用户操作
- **那么** 系统不得发起任何对 OTX 的 HTTP 调用（无自动演绎驱动）

#### 场景:一键处理失败可重试
- **当** 某笔挂起事项因 OTX 不可达处理失败
- **那么** 该事项保持原状态并记录失败日志，其余事项继续处理，下次一键处理可重试

### 需求:系统必须模拟链上事件与确认数演化

系统必须（MUST）提供链上事件模拟器：内存维护区块高度与模拟交易，交易确认数随区块推进递增；**区块推进仅在「一键处理」时按需执行（advanceTo），无定时自动推块**。当交易确认数达到配置阈值时，自动触发 OTX 充值入账。

#### 场景:充值交易确认达标后自动入账
- **当** 一键处理推进区块使某笔充值交易确认数达到阈值（默认 12）
- **那么** 模拟器必须自动调用 `POST /deposit`（携带 uid/amount/bizNo/currency/chainId/chainTxHash）
- **那么** 操作日志必须输出该步骤的业务身份、调用端点与 OTX 响应结果

#### 场景:确认数未达标不入账
- **当** 一笔充值交易的确认数尚未达到阈值
- **那么** 模拟器不得调用充值入账接口，页面展示当前确认数/所需确认数

#### 场景:区块仅在处理时推进
- **当** 应用空闲（无一键处理触发）
- **那么** 模拟链区块高度不得自动增长

### 需求:系统必须支持提现业务动作

系统必须（MUST）支持通过个人中心手动触发的提现动作，覆盖"申请提现（冻结）→ 一键处理（广播 → 确认 → 结算）"与"申请提现 → 取消提现（标记）→ 一键处理（解冻）"两条业务路径；每个动作必须输出业务身份说明、调用端点与响应结果到操作日志。

#### 场景:申请提现
- **当** 用户在页面提交 `POST /withdrawals`（uid/金额）
- **那么** 系统必须调用 `POST /withdraw/freeze` 完成冻结，创建提现记录并置状态为已冻结（FROZEN）

#### 场景:一键处理完成提现结算
- **当** 用户点击一键处理且存在已冻结提现
- **那么** 系统必须依次调用 `POST /withdraw/broadcast`、`POST /withdraw/{bizNo}/confirm-settle`
- **那么** 提现记录置为已结算（SETTLED），操作日志记录每个步骤

#### 场景:取消提现标记与解冻
- **当** 用户在记录列表对未结算提现提交 `POST /withdrawals/{bizNo}/cancel`
- **那么** 系统必须仅置记录为取消处理中（CANCEL_PENDING），不直接调用 OTX
- **当** 再次点击一键处理
- **那么** 系统必须调用 `POST /withdraw/{bizNo}/cancel` 完成解冻，记录置为已取消（CANCELLED）

#### 场景:已结算提现不可取消
- **当** 用户对已结算（SETTLED）提现提交取消
- **那么** 系统必须拒绝并记录错误日志，不产生任何 OTX 调用
