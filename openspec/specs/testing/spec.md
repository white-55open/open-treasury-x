# testing 规范

## 目的

本规范定义项目级单元测试标准，目标是让测试可读、可维护、可审计，并能够直接表达业务意图。

本规范适用于所有模块的单元测试；集成测试、端到端测试、契约测试应另行定义，不得混用本规范的断言粒度。

## 需求

### 需求:每个测试必须清晰表达意图

每个测试方法必须通过方法名或 `@DisplayName` 明确说明场景与期望结果，读者无需查看实现即可理解该测试要验证什么。

#### 场景:测试名称能够直接描述行为
- **当** 编写一个测试用例
- **那么** 测试名称必须包含对象、场景和预期结果，禁止使用 `test1`、`shouldWork`、`happyPath` 这类含糊命名

#### 场景:失败信息能反推业务意图
- **当** 测试失败
- **那么** 失败日志和断言信息必须能让开发者快速判断是哪个业务约束被破坏

### 需求:测试命名必须遵循统一格式

测试方法名应优先采用 `should_<expected>_when_<condition>` 或 `given_<condition>_should_<expected>` 风格；若项目采用中文显示名，则 `@DisplayName` 必须与方法名语义一致。

#### 场景:方法名与显示名一致
- **当** 测试方法使用英文命名时
- **那么** `@DisplayName` 不得与方法名表达相反含义

#### 场景:参数化测试也必须可读
- **当** 使用参数化测试
- **那么** 每组参数必须带有可读的 case 名称，不能只显示原始入参值

### 需求:单元测试必须遵循 AAA 结构

每个单元测试必须保持 Arrange-Act-Assert 结构，测试准备、触发动作、结果断言三段职责清晰分离。

#### 场景:测试准备与断言分离
- **当** 编写单元测试
- **那么** Arrange 阶段不得包含业务动作，Assert 阶段不得混入额外准备逻辑

### 需求:一个测试只验证一个核心行为

每个测试必须聚焦单一业务规则或单一失败路径，禁止在同一测试中混合多个互不相关的断言目标。

#### 场景:多个业务规则应拆分
- **当** 一个测试同时验证多个异常分支或多个状态变化
- **那么** 应拆分为多个独立测试，以便失败定位

### 需求:单元测试必须保持确定性

单元测试不得依赖真实网络、真实数据库、真实时间、随机数或外部共享状态；必要时必须通过 mock、stub、fake 或固定时钟注入隔离依赖。

#### 场景:测试结果可重复
- **当** 同一测试重复执行
- **那么** 结果必须稳定一致，不得依赖执行顺序或执行时机

### 需求:断言必须精确且贴近业务规则

断言应直接验证业务不变量、异常类型、错误码、状态变化和关键返回值；不得只断言“未抛异常”或“调用成功”这类空洞结果。

#### 场景:异常测试必须校验异常语义
- **当** 业务规则要求抛异常
- **那么** 测试必须同时校验异常类型和关键业务错误码或错误消息

#### 场景:状态测试必须校验前后变化
- **当** 业务动作会修改实体状态
- **那么** 测试必须断言修改前后的关键字段变化，而不是只断言方法返回值

### 需求:测试边界必须围绕业务不变量

单元测试应优先覆盖以下高风险边界：空值、非法值、边界值、幂等性、并发冲突、重复提交、状态机非法转换、金额或数量精度问题。

#### 场景:边界条件覆盖完整
- **当** 领域对象或服务存在明确不变量
- **那么** 单元测试必须覆盖正向与反向场景，不能只覆盖 happy path

### 需求:测试代码必须保持企业级可维护性

测试代码应避免过度共享 fixture、隐式魔法值和脆弱的全局状态；公共测试数据应通过工厂方法或 builder 显式构造。

#### 场景:测试夹具可读可复用
- **当** 多个测试复用相同准备数据
- **那么** 应提取为明确命名的测试工厂方法，而不是复制粘贴或隐藏在静态全局变量中

### 需求:测试分层必须清晰

单元测试只验证单个类、单个聚合或单个服务的本地行为；跨模块流程、真实 Spring 装配、数据库读写和 HTTP 路由应归入集成测试或接口测试。

#### 场景:测试类型不得混淆
- **当** 测试需要启动完整应用、访问真实数据库或调用 HTTP 接口
- **那么** 该测试不得标记为单元测试

## 约束

- 禁止使用无意义命名的测试方法。
- 禁止在单元测试中依赖执行顺序。
- 禁止以覆盖率数字替代行为断言质量。
- 禁止把多个独立失败原因塞进一个测试。
- 禁止在测试中隐藏业务意图，测试名必须可作为规范文档阅读。
